Persistent context (always visible, every screen)

Server identity
localhost:8080 · engine v0.4.2 · mode: mock
Readiness vs liveness
process-up · ready · not-ready · unreachable · stale (last refresh timestamp always shown)
Tenant / role
acme-prod · editor (or “local mode — unauthenticated”, an explicit state, not a synthetic viewer)
Revision
Resource-specific ETag/hash on the resource header. No global server revision exists — the shell shows “revision: per-resource”, never a manufactured global number.
Execution mode
“Active configuration” badge wherever a run can be triggered. Never “safe”, “isolated”, or “no egress”.

Object model

Server → Tenant → {Agent, Pipeline} → Revision (ETag) → Run (session_id, nodes[], latency ns) → Log record (session-grouped) → Export snapshot. Runs reference the pipeline by name, not a pinned revision — the UI says so rather than implying pinning.

Command palette (⌘K)

Navigate sections, open a mock by name, jump to a session ID, copy SDK base URL, toggle theme. Palette actions are the same actions as the visible UI — it never exposes anything role-gated that the chrome hides, and every action is reachable without it (it is an accelerator, not the only path).

2 · Primary user journey (Release A — “safe first success”)

  1. Connect to existing local server → shell shows identity, readiness, last refresh UX-02
  2. Overview surfaces the documented starter agent + copyable SDK settings UX-02
  3. Open starter agent in Mocks → full server definition loads (never regenerated from the summary type) UX-03
  4. Edit a scenario response — linked form + YAML views of one draft UX-03
  5. Validate → schema errors are line-anchored and actionable UX-03
  6. Review diff (before/after), explicit Apply with If-Match precondition UX-03
  7. Receipt states clearly: persisted to disk vs runtime-only UX-03
  8. Test Lab → preconfigured pipeline → “Run against active configuration” with input + fresh session ID UX-05
  9. Inspect node results: nodes[] with node_id, agent_name, response (nullable), latency converted from nanoseconds; parallel order labelled “definition order, not chronology” UX-05
  10. 422 partial failure → inspect optional result + error; failed node highlighted UX-05
  11. Investigate → session-grouped provider logs where available (no fabricated run↔log links) UX-04
  12. Export bounded run evidence — snapshot scope, completeness, omissions stated UX-06

Empty-install variant: onboarding checklist explains pipeline creation is not in Release A and links CLI/YAML setup guidance. The Run button never appears dead; it appears only when a pipeline exists.

Non-happy paths designed alongside (not after)

invalid-schemaline-anchored errors; Apply disabled with reason; draft kept
viewer-denied403: editing visibly locked with role explanation — not broken, not hidden
conflict (stale edit)ETag mismatch: both drafts preserved; “reload current” vs reviewed overwrite; nothing silently discarded
disconnectedunreachable ≠ empty catalog; reads frozen with staleness stamp; no auto-retry of stateful runs
runtime-only savereceipt distinguishes durable file write from in-memory apply; file failure ≠ durable save
missing fixturerun blocked with named missing dependency and setup guidance
partial failure (422)completed nodes shown as evidence; failed node error; absent nodes “unknown”, not zero
empty log store“no records in window” with window shown — distinct from unreachable and unauthorized
unknown outcomeconnection lost mid-run: outcome unknown; manual re-check only, duplicate submission disabled
unsupported versionGUI/backend mismatch: safe reads allowed, unsupported writes disabled, drafts exportable

3 · Two visual directions

Both are built on the binding design-system tokens (same palette, type stack, status colors) and both are dense-and-calm per the brief — they differ in structure, density, and how trust-context is carried. Each is a real rendered screen of the same content: the Release A Overview (UX-02) with readiness, starter, empty-pipeline guidance, and recent failures.

Direction A — “Instrument”Direction B — “Worksheet”
context carrierFull-width system status strip pinned above content: server, readiness, tenant/role, mode, freshness as instrument cellsContext woven into a page-level “connection receipt” card; slim topbar
densityCompact 13px base, 32px rows; tables dominate; maximal rows per viewport14px base, 40px rows; sectioned cards with generous gutters; scannable groups
shape languageSquared (4px radii), hairline borders, flat; mono-forward labelsSofter (8–10px radii), subtle elevation on interactive surfaces only
status languageCoded chips: READY / NOT-READY — terse, uppercase mono + dot + textSentence-case badges with icon + text (“Ready · checked 4s ago”)
best forOperators/developers living in the tool; maximum scanning throughputMixed personas incl. reviewers; progressive disclosure reads more naturally
riskCan feel severe to occasional reviewersSlightly fewer rows per screen for power users

Recommendation: Direction B (“Worksheet”), with Direction A's instrument strip adopted for the persistent context header. The brief spans five personas with progressive disclosure; B carries narrative states (receipts, completeness banners, guidance) more naturally, while A's strongest element — the always-on truth strip — transplants cleanly.

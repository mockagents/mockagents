## 5. Design observations

1. **Two validation authorities, one of them loose (F3 persists).** Go is what runs, the schema is what editors/GUI show, and only the chaos/strict-tools enums are cross-checked. Generating every schema from Go types (`tools/contractcheck` already does it for two kinds) plus strict decoding in the loaders would close C-04, C-08, C-19 and C-20 together.
2. **"Load" and "validate" are separate steps that each caller re-assembles.** `validate`, `start`, `test`, `mcp`, `a2a`, `mcp --manage`, the watcher, the write API and `ValidateBytes` each pick which validators to run; `mcp`/`a2a` skip them entirely (C-02) and `start` skips cross-document checks (only warns at registry time). A single `config.LoadAndValidate(dir, opts) (*Documents, Report)` used everywhere would make the CLI surfaces agree by construction.
3. **Fail-open vs fail-closed is decided per knob.** `env.go` declares a strict contract; `NormalizeLogBodyMode`, the session/audit caps and `MOCKAGENTS_OTEL_STDOUT` still fail open (C-05, C-17). A lint over `os.Getenv` call sites (all must go through `env.go`) would keep it consistent.
4. **The CLI has no output contract.** stdout/stderr split, JSON mode, colors and exit codes differ per subcommand (C-10, C-16, C-25). A small `cli.Reporter` (text/json, TTY-aware, one exit-code enum 0/1/2) shared by validate/test/contract/drift would make the CI story testable.
5. **Destructive operations run without confirmation.** `init --force` and `rm` both delete user-authored files with no confirmation (C-03, C-07). Both should only touch files they own, and ask before deleting anything else.
6. **Silent filtering in the directory scan** (dependency/dot dirs, nested-file sniffing, first-document-only) makes "what got loaded" hard to see. `validate -v` listing every file loaded, skipped or ignored, with the reason, would cover C-01, C-11 and C-22 at little cost.
